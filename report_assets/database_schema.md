# MongoDB Database Schema Documentation

**Database Name:** `anomaly_detection`  
**Primary Collection:** `sensor_readings`  
**Driver / ODM:** `PyMongo` via FastAPI backend services

---

## 1. Document Structure & Field Definitions

Each document in `sensor_readings` captures an individual machine telemetry packet alongside the real-time scoring outputs generated by both ML models.

```json
{
  "_id": "ObjectId('66bf48e1a89c201d48c081e2')",
  "timestamp": "2026-08-17T17:15:30.402704+00:00",
  "machine_id": "L47230",
  "air_temp": 298.9,
  "process_temp": 309.1,
  "rpm": 2861.0,
  "torque": 4.6,
  "tool_wear": 143.0,
  "true_failure": 1,
  "iso_score": 0.61801,
  "iso_flag": 1,
  "ae_score": 1.78196,
  "ae_flag": 1,
  "is_anomaly": true
}
```

---

## 2. Field-by-Field Reference

| Field Name | Type | Unit / Range | Description & Purpose |
|---|:---:|:---:|---|
| `_id` | `ObjectId` | BSON 12-byte | Auto-generated unique MongoDB primary identifier. |
| `timestamp` | `String` (ISO 8601) | UTC Timestamp | Ingestion timestamp recorded at edge transmission. Indexed for chronological queries. |
| `machine_id` | `String` | e.g. `"L47230"` | Identifier of the physical machine or CNC asset emitting telemetry. |
| `air_temp` | `Float` | $295.0 - 305.0\text{ K}$ | Ambient room temperature surrounding the machine equipment. |
| `process_temp` | `Float` | $305.0 - 315.0\text{ K}$ | Internal machine process operating temperature (typically $\approx 10\text{ K}$ above air temp). |
| `rpm` | `Float` | $1100 - 2900\text{ RPM}$ | Spindle rotational speed. Inversely coupled with torque under normal operating conditions. |
| `torque` | `Float` | $3.0 - 80.0\text{ Nm}$ | Torque applied to the tool during the machining cycle. |
| `tool_wear` | `Float` | $0 - 260\text{ min}$ | Cumulative tool operating duration in minutes. Increases monotonically. |
| `true_failure` | `Integer` | `0` or `1` | Ground-truth machine failure status from the dataset (**see special rationale below**). |
| `iso_score` | `Float` | $0.35 - 0.75$ | Continuous anomaly score computed by Isolation Forest (negated path length; higher = more anomalous). |
| `iso_flag` | `Integer` | `0` or `1` | Discrete trigger flag: `1` if Isolation Forest marks the point as anomalous ($>3.4\%$ contamination threshold). |
| `ae_score` | `Float` | $0.05 - 5.0+$ (MSE) | Autoencoder vector reconstruction error across all 5 normalized features. |
| `ae_flag` | `Integer` | `0` or `1` | Discrete trigger flag: `1` if reconstruction error exceeds $\mu + 2\sigma$ ($0.62011$). |
| `is_anomaly` | `Boolean` | `true` / `false` | Final ensemble alert trigger (`iso_flag == 1 OR ae_flag == 1`). Controls dashboard alerts. |

## 3. Rationale for Storing `true_failure`

> [!IMPORTANT]
> **Why store `true_failure` if real-world deployments do not have future labels?**
>
> In an actual physical factory deployment, the system must operate in a purely unsupervised capacity — ground-truth labels do not exist ahead of a breakdown.
>
> In this simulation environment, `true_failure` is retained for **live empirical validation**:
> 1. **Live Precision / Recall Computation:** It allows the `/readings/model-comparison` endpoint to compute live confusion matrices, precision, recall, and F1-scores as simulated telemetry streams into MongoDB.
> 2. **Comparative Model Study:** It enables objective verification of whether the Autoencoder or Isolation Forest catches real physical failures (such as Heat Dissipation Failure or Overstrain Failure) in practice.
> 3. **Supervised vs Unsupervised Auditing:** It ensures that although training was conducted unsupervised (models never saw labels during training), we can quantitatively prove the safety efficacy of the pipeline.

## 4. Indexing & Query Optimization Strategy

To maintain responsive query times (<5ms) as the collection accumulates tens of thousands of readings, two indexes are enforced in `backend/app/database.py`:

```javascript
// Index 1: Fast reverse chronological retrieval for live line charts
db.sensor_readings.createIndex({ "timestamp": -1 });

// Index 2: Compound index for quick anomaly filtering & pagination
db.sensor_readings.createIndex({ "is_anomaly": -1, "timestamp": -1 });
```
